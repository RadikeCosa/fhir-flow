- `config/fhir.config.ts`: Centraliza y valida la configuración para conectar la aplicación con el servidor FHIR R4. Define la URL base (desde la variable de entorno `FHIR_BASE_URL`), la versión FHIR, cabeceras HTTP por defecto, parámetros de paginación y las capacidades soportadas por el servidor. Esta configuración se utiliza exclusivamente en la capa de infraestructura para asegurar conexiones consistentes y seguras con el servidor FHIR.

- `types/env.d.ts`: Define el tipado estricto para las variables de entorno utilizadas en la aplicación, especialmente `FHIR_BASE_URL`. Esto asegura que el acceso a variables de entorno sea seguro y explícito en TypeScript, evitando errores por nombres incorrectos o valores inesperados. Este archivo solo contiene definiciones de tipos y no realiza validación en tiempo de ejecución.

- `lib/fhir/fhir-client.ts`: Implementa el único cliente HTTP autorizado para comunicarse con el servidor FHIR R4. Centraliza todas las solicitudes de red, usando la configuración definida en `config/fhir.config.ts`. Maneja errores HTTP y respuestas FHIR OperationOutcome de forma tipada y explícita. No contiene lógica de dominio ni mapeo de modelos; solo gestiona la comunicación y normalización de respuestas FHIR. Este cliente debe ser utilizado exclusivamente desde la capa de infraestructura, asegurando que la UI y el dominio nunca interactúen directamente con FHIR ni con la red.

- `lib/fhir/bundle-utils.ts`: Proporciona utilidades seguras para trabajar con Bundles FHIR. Emplea esquemas Zod mínimos para validar fragmentos y ofrece helpers para extraer entradas y recursos, obtener el campo `total`, resolver enlaces de paginación (`self`, `next`, `prev`) y filtrar recursos por `resourceType`. Devuelve valores por defecto en casos de bundles inválidos o faltantes en lugar de lanzar, y está diseñado para usarse en la capa de infraestructura antes de la validación y mapeo hacia los modelos de dominio.

- `domain/patient.ts`: Define el modelo de dominio `Patient`, que representa la entidad paciente de forma independiente a FHIR y cualquier estándar externo. Este modelo es simple, estable y UI-friendly, pensado para ser consumido por la lógica de negocio y la interfaz, sin exponer detalles técnicos de FHIR. Incluye campos como identificador, nombre, fecha de nacimiento normalizada, género (con valores propios del dominio), contacto y dirección. La razón de agregarlo en este momento es establecer una base clara y desacoplada para la lógica de negocio, permitiendo que la infraestructura mapee y normalice datos externos (FHIR) hacia este modelo, y así mantener la arquitectura limpia y testable. Este archivo es fundamental para asegurar que el dominio permanezca estable y que los cambios en FHIR o en la infraestructura no afecten la lógica central de la aplicación.

- `domain/patient.repository.ts`: Declara la interfaz de repositorio para el agregado `Patient` en el dominio. Define el contrato para acceder y consultar pacientes de forma desacoplada de la infraestructura (FHIR, base de datos, etc.), asegurando que la lógica de negocio nunca dependa de detalles externos. Incluye tipos para paginación, filtros y resultados paginados, permitiendo búsquedas flexibles y extensibles. La interfaz expone métodos explícitos para obtener pacientes por ID y para realizar consultas con filtros y paginación, facilitando la testabilidad y el mantenimiento. Se agrega en este momento para establecer una frontera clara entre dominio e infraestructura, y para que cualquier implementación (por ejemplo, sobre FHIR) deba respetar el modelo y las reglas del dominio, manteniendo la arquitectura limpia y orientada a negocio.

- `infrastructure/fhir/schemas/patient.schema.ts`: Define el esquema Zod para validar recursos FHIR Patient en el límite de infraestructura. Este esquema es permisivo y solo valida los campos que el mapper de dominio necesita consumir, evitando acoplar el dominio a la estructura FHIR. Garantiza que los datos externos sean seguros y predecibles antes de mapearlos al modelo de dominio. Se agrega en este momento para asegurar la validación estricta y desacoplada de datos FHIR, cumpliendo la regla de validación en tiempo de ejecución y evitando que detalles FHIR se filtren al dominio.

- `infrastructure/fhir/mappers/patient.mapper.ts`: Implementa el mapper que transforma un recurso FHIR Patient validado en el modelo de dominio `Patient`. Extrae y normaliza identificador, nombre, género, fecha de nacimiento, contacto y dirección, aplicando reglas de negocio y valores por defecto según corresponda. Asume que la validación ya ocurrió y nunca expone estructuras FHIR fuera de la infraestructura. Se agrega para cumplir la capa de anti-corrupción, asegurando que el dominio solo reciba datos limpios, normalizados y desacoplados de FHIR, manteniendo la arquitectura hexagonal y la testabilidad.

- `infrastructure/fhir/patient.fhir-repository.ts`: Implementa la clase PatientFhirRepository, que cumple el contrato PatientRepository del dominio usando el servidor FHIR como fuente de datos. Orquesta la búsqueda, validación (con Zod) y mapeo de recursos FHIR Patient hacia el modelo de dominio, asegurando que la lógica de negocio nunca consuma datos sin validar ni estructuras FHIR. Centraliza la construcción de parámetros de búsqueda, el manejo de paginación y la gestión de errores HTTP, manteniendo todas las preocupaciones de infraestructura aisladas. Se agrega para materializar la capa de anti-corrupción y permitir que el dominio trabaje con pacientes de forma desacoplada y segura, siguiendo los principios de arquitectura hexagonal.

- `infrastructure/fhir/patient.factory.ts`: Expone una fábrica para crear instancias de PatientRepository respaldadas por FHIR. Centraliza la composición y el wiring de dependencias en la infraestructura, permitiendo inyectar un FhirClient personalizado (útil para tests o configuración avanzada) o usar uno por defecto. Garantiza que el resto de la aplicación dependa solo de la interfaz PatientRepository, nunca de detalles de infraestructura ni de FHIR, reforzando la separación de capas y la testabilidad.
